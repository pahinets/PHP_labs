# ЛР7 — результати контрольованих вимірювань, 26.11.2026

Windows, PHP 8.5.11 built-in server, MariaDB 11.4.5, ApacheBench 2.3.
Seed з `seed.sql`: 1000 тем / 100 авторів, по 10 тем автора, 50 pinned.
Усі **9 прогонів ab**: `-n 200 -c 20`, Complete requests=200,
Failed requests=0, Non-2xx=0. Це локальний навчальний дослід, не production capacity.

## 1. Індекс: однаковий SQL та URL

URL в обох станах:

```text
api.php?resource=topics&mode=original&author=author_042
```

Виконано саме `explain.sql`; значення параметра `:author` підставлено буквально:

```sql
EXPLAIN
SELECT t.id, t.title, t.author, t.created_at, t.is_pinned
FROM topics t
WHERE t.author = 'author_042'
ORDER BY t.id DESC;
```

| Стан | id | select_type | table | type | possible_keys | key | key_len | ref | rows | Extra |
|---|---:|---|---|---|---|---|---|---|---:|---|
| До | 1 | SIMPLE | t | index | NULL | PRIMARY | 4 | NULL | 1000 | Using where |
| Після | 1 | SIMPLE | t | ref | idx_topics_author | idx_topics_author | 202 | const | 10 | Using where |

До індексу `ORDER BY id DESC` дозволяє повне сканування PRIMARY, тому тут
**index, не ALL**. Після `create_index.sql` та `ANALYZE TABLE topics` — ref
за author. `rows` — оцінка оптимізатора, не виміряна кількість фізичних читань.
Індекс не обіцяє прискорити старий `q` з `LIKE '%...%'`.

| Стан | PHP, мс (медіана 10) | Пік, МБ | SQL | Кеш | RPS (медіана 3) |
|---|---:|---:|---:|---|---:|
| Без author-індексу | 13.616 | 2 | 1 | NONE | 134.93 |
| З author-індексом | 13.833 | 2 | 1 | NONE | 183.20 |

Всі прогони, без вибору «найкращого»:

| Стан | Прогін | RPS | ab Time per request, мс (mean, з чергою) |
|---|---:|---:|---:|
| До | 1 | 134.93 | 148.229 |
| До | 2 | 136.58 | 146.438 |
| До | 3 | 109.12 | 183.293 |
| Після | 1 | 144.82 | 138.100 |
| Після | 2 | 201.06 | 99.472 |
| Після | 3 | 183.20 | 109.169 |

У цій серії медіанний RPS зріс на 35.8%, але медіана PHP **не покращилася**
(13.616 → 13.833 мс). Є помітний розкид і накладні витрати PHP/HTTP/планувальника;
не слід обіцяти універсальний приріст RPS або приховувати результат часу PHP.
План переконливо показує зміну доступу 1000 → 10 оцінених рядків.
Built-in PHP у Windows послідовний: `-c 20` створює чергу клієнтів, не workers.

## 2. N+1: індекс однаковий в обох режимах

Той самий seed, індекс author **вже є і не змінюється**.
`mode=before` та `mode=after` без фільтра повертають 1000 тем із кількістю тем автора.

| Режим | PHP, мс (медіана 10) | SQL | RPS (один ab) | ab mean, мс |
|---|---:|---:|---:|---:|
| before: N+1 | 211.178 | 1001 | 4.44 | 4506.828 |
| after: GROUP BY/JOIN | 5.079 | 2 | 84.67 | 236.215 |

JSON побайтово однаковий, SHA-256
`2f0f69073639784afcabe93edb61cb44e803b2b8b9d90946b05500978cbca51b`.
Це не дослід індексу і не порівняння з початковою ЛР6, де список уже мав 1 SQL.
Старі числа 379.60/5.05 мс змішували зміну N+1 та індексу; нові заміри їх замінюють.
