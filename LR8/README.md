# Практикум 8 — аудит безпеки PHP, варіант 9

Фінальна версія форуму з ЛР7. Захист також підключений до маршрутів ЛР1–7:
не можна обійти роль модератора через старий `api_add.php`, `add.php` чи `edit.php`.
Звіти DOCX/PDF, тести, паролі, резервні копії та логи до GitHub не додаються.

## Запуск

Потрібні PHP 8.1+ з `pdo_mysql`, `mbstring`, MySQL/MariaDB.
Зберігайте структуру всього репозиторію: спільні `security.php`, `security.js`,
`auth.php`, `moderator.php`, `database.php` лежать поряд із папками `LR*`.
Локальні назви папок — `Practicum01`…`Practicum08`.

1. Імпортуйте `schema.sql` у MySQL (база `practicum4`). Скрипт ЛР8 не видаляє таблиць.
   Не запускайте старий навчальний `LR4/schema.sql` над потрібними даними.
2. За потреби задайте `PHP_LAB_DSN`, `PHP_LAB_DB_USER`, `PHP_LAB_DB_PASSWORD`
   у середовищі процесу PHP. Типові параметри попередніх робіт:
   `mysql:host=localhost;dbname=practicum4;charset=utf8mb4`, користувач `root`, порожній пароль.
   Це лише локальний навчальний стенд, не параметри публічного сервера.
3. Налаштуйте власний пароль модератора. У PowerShell, з кореня репозиторію:

   ```powershell
   $password = Read-Host 'Пароль модератора' -MaskInput
   $env:PHP_LAB_MODERATOR_HASH = $password | php -r '$p=rtrim(stream_get_contents(STDIN), "\r\n");echo password_hash($p,PASSWORD_DEFAULT);'
   Remove-Variable password
   php -S 127.0.0.1:8008 -t .
   ```

   Не публікуйте пароль або хеш у коді/README. Якщо змінна не встановлена,
   читання та звичайне створення доступні, вхід модератора повертає 503.
4. Відкрийте `http://127.0.0.1:8008/LR8/index.html`
   (локально — `/Practicum08/index.html`). Вхід/вихід — `/moderator.php`.
   Запускати webroot лише всередині `LR8` не можна: спільні захисні файли будуть недоступні.

## Права і CSRF

| Запит | Доступ |
|---|---|
| GET список/одна тема/закріплені | усім |
| POST створити звичайну тему | CSRF-токен поточної сесії |
| POST `action=pin` | CSRF + модератор |
| POST створити з `is_pinned=1` | CSRF + модератор |
| ЛР4: редагування та видалення | CSRF + модератор; GET не змінює БД |

`GET /auth.php` повертає `{success:true,data:{csrf_token,moderator}}`.
У POST передайте `X-CSRF-Token` або поле форми `csrf_token` з тією самою cookie
`FORUMSESSID`. `POST /auth.php` з `action=login,password` або `action=logout`
також вимагає CSRF. Після входу/виходу ID сесії та токен змінюються:
відкриту раніше вкладку треба оновити. `security.js` не повторює POST автоматично.
Клієнт не може призначити собі роль параметром `role` чи `is_moderator`.

Сесія модератора діє 30 хвилин. Cookie: HttpOnly, SameSite=Lax, Secure на HTTPS.
У локальному HTTP Secure вимкнено, інакше браузер не надсилав би cookie.
П'ять неправильних паролів блокують наступні спроби цієї сесії на 60 с.
Це не глобальний захист від перебору: нова cookie обходить такий ліміт.
Для production потрібні HTTPS, зовнішній rate limit і повноцінне управління обліковими записами.

## Результати аудиту «до → після»

| Перевірка | До | Після |
|---|---|---|
| POST без CSRF | форми 1–3 приймали дані; API 5–7 не перевіряли токен | 403, запис не змінюється |
| Гість + `is_pinned=1` | 201 в API 5–7; створення через ЛР4 також успішне | 403 на всіх маршрутах |
| Гість + edit/delete ЛР4 | не було серверної перевірки ролі | 403 навіть із власним валідним CSRF |
| Помилка PDO/direct db.php | у 7 видно SQLSTATE, шлях, stack trace при display_errors=1 | загальне повідомлення, деталі лише в error_log |
| SQLi `' OR '1'='1` у author/q | PDO-параметри вже були в ЛР4–7; вразливість не підтверджена | прив'язування збережене, payload не розширює вибірку |
| `<script>alert(1)</script>` у title | HTML екранувався; JS використовував textContent | лишається текстом, виконуваних script у results немає |
| `<img src=x onerror=alert(1)>` | додаткова перевірка контекстів | екранований текст у списку/атрибуті edit ЛР4 |

У формі видалення ЛР4 прибрано динамічну назву з inline JavaScript:
підтвердження тепер має сталий текст. Не заявляємо, що ця заміна сама по собі
доводить наявність успішного XSS у попередній реалізації.

Валідація ЛР6–8: title 5–100 і author 1–50 Unicode-символів після trim;
масиви/числа замість рядків, порожні та надто довгі значення — 400.
ЛР5 зберігає свій контракт (успіх без обгортки, помилки полів 422).
ЛР1–3 зберігають суворіші правила навчальної HTML-форми.
Екранування не замінює валідацію, а валідація — екранування.

## Збережені можливості ЛР7

`GET api.php?resource=topics`: `mode=after` (типово) — 2 SQL,
`mode=before` — навчальний N+1, `mode=original` — 1 SQL без лічильника автора.
Індекс `idx_topics_author`, GROUP BY/JOIN і профільні HTTP-заголовки збережені.
`GET api.php?resource=topics&action=pinned`: файловий кеш TTL 60 с,
MISS — 1 SQL, HIT — 0 SQL. Файл поза webroot; каталог можна задати
`PHP_LAB_CACHE_DIR`. ЛР4–8 використовують спільну ідентичність БД/кешу,
записи через старі маршрути теж інвалідують кеш.
Зовнішні зміни БД без застосунку стають видимими після TTL.

## Перевірка

Локально виконано 18 автоматизованих тестів, перевірено синтаксис PHP/JS,
відкрито всі вісім головних сторінок, перевірено cookie/ротацію токенів,
ролі, stored XSS, SQLi та інвалідацію кешу між лабораторними.
Браузер підтвердив 403 для POST без токена та нуль виконуваних script у списку.
Це обмежений аудит навчального застосунку, не сертифікація повної безпеки.

Фінальна незалежна перевірка додатково виявила прямий доступ до шаблону
`topic_form.php` і мовчазне приймання некоректного `is_pinned` у ЛР5:
тепер це відповідно 404 без технічних деталей і 422 без створення запису.
Відкладене покращення інтерфейсу: кнопка «Закріпити» ще видима гостю,
але сервер завжди відхиляє таку дію з 403.
